## Implemented boundaries

The first completed introduction consumes the learner–mentor free allowance. Paid follow-ups require a completed introduction with that exact mentor. Pricing is an integer paise snapshot per session; subsequent mentor price changes do not alter an existing checkout. New paid checkouts close fifteen minutes before the session starts. One pending checkout per learner and a bounded checkout creation rate limit reservation abuse.

Booking state distinguishes awaiting payment, confirmed, completed, cancelled and expired. Active paid reservations protect the slot and both participant roles. A short transaction-level scheduling lock gives reservation mutations a consistent order and releases expired reservations before new booking attempts. This deliberately serializes scheduling mutations for the campus pilot; it is a known throughput limit, not a measured production scalability claim. Network calls never hold the scheduling lock.

Trusted payment RPCs are executable only by the service role. Actual hosted privilege queries confirmed no anonymous/authenticated execution on all nine payment RPCs. Clients receive participant-only payment summaries, without provider identifiers. Private orders, captures, events and jobs have RLS enabled and no direct client grants. Owner pricing and reservation RPCs derive the caller from auth.uid(). Advisor INFO findings for private tables without policies are intentional deny-direct access; authenticated definer findings for narrow owner RPCs are reviewed alongside existing RPC findings. Guidance: [intentional authenticated definer APIs](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).

The server verifies the Checkout HMAC using the stored order ID, then fetches provider order/payment state and verifies capture, amount and currency. A browser success flag or payment authorization cannot confirm a session. Webhooks validate raw-body HMAC and record successfully processed event IDs. Duplicate callbacks/events are safe, and failed events do not reverse capture. Callback and webhook bodies have bounded sizes; authenticated mutations require the configured same-origin Origin header. Secrets remain server-only; live key IDs are refused.

Refund intent is durable in the cancellation/late-capture transaction. Refund retries reuse a provider idempotency key and reconcile existing provider refunds before retrying uncertain requests. Fully refunded payments revoke confirmed meeting access even while the provider refund list is still propagating. Refund jobs have leases, backoff, bounded retries and review states. A closed browser cannot be the only mechanism responsible for reconciliation: a private worker command is supplied and must be scheduled operationally.

On 19 November the owner configured all four values privately in .env.local. Read-only requests authenticated successfully with Razorpay test keys and the Supabase server secret. A temporary Cloudflare tunnel forwards only the webhook POST path through a loopback relay; other app paths return 404. Public DNS resolved the tunnel, although the laptop's default DNS initially did not; the HTTPS probe retained normal TLS hostname verification while connecting to the publicly resolved address.

An actual Razorpay Standard Checkout test used Riya and Aarav, with an INR 199 follow-up after their completed introduction. The mock bank Failure action produced a failed provider payment while Nexus remained awaiting payment. Retrying the same order with the mock bank Success action produced one captured payment and exactly one booking confirmation. The browser displayed Payment confirmed. This used Razorpay's sandbox API and checkout, with no real funds. Booking reference: `80b65fbb-6cad-49ee-a257-8f055a871d8a`.

After a second actual sandbox payment, a scoped retry with the unchanged idempotency key was accepted. Razorpay processed the full INR 199 refund (`rfnd_U25sgl42OilNnU`), and its signed refund webhook moved Nexus to refunded. The browser displayed Full refund processed. No API payload or credential change was needed; the cause of the earlier generic rejection is not conclusively established.

The isolated browser deliberately blocked that checkout's verification and status endpoints before completing the mock bank Success flow. Razorpay captured the payment, two real signed webhooks reached the relay and returned HTTP 200 in 2,398 ms and 2,322 ms, and Nexus confirmed the booking. Three actual provider deliveries were verified separately from the named synthetic probes. This proves payment confirmation without a working browser callback and provider-driven refund completion. The failure payment UI was verified in the earlier checkout; this run does not claim to have induced all five subscribed event types, especially refund.failed.
